# 架构思维优先

## 核心原则

**修改代码前，先思考架构层面的解决方案，而不是急于在表面问题上打补丁。**

## 触发场景

当你发现需要：
- 在多个地方添加相同的代码
- 在多个调用点设置同一个字段
- 在多个文件中重复相同的逻辑

**停下来！** 这通常意味着你应该在更底层统一处理。

## 思考清单

在动手修改前，先问自己：

1. **这个字段/逻辑的含义是什么？**
   - 它代表什么业务概念？
   - 它的生命周期是什么？

2. **设置/触发的时机是什么？**
   - 什么时候应该设置/执行？
   - 有哪些场景会触发？

3. **谁应该负责这个逻辑？**
   - 哪一层最了解这个上下文？
   - 放在哪一层最符合职责划分？

4. **放在哪里最合适？**
   - 放在更底层是否能覆盖所有场景？
   - 新增调用点是否会遗漏？
   - 是否符合"单一职责"原则？

## 反模式 vs 最佳实践

### 反模式：症状修复

```
问题：files_downloaded 字段没有设置
做法：在所有创建 PackageVersion 的地方添加设置
结果：10+ 个文件需要修改，新增上传路径容易遗漏
```

### 最佳实践：架构思维

```
问题：files_downloaded 字段没有设置
分析：
  - 含义：文件是否已存储在本地
  - 时机：当文件被存储时
  - 负责：repository 层负责存储
做法：在 repository 的 StorePackageFile 中统一设置
结果：只需修改 1 处，新增路径自动覆盖
```

## 常见场景

| 场景 | 症状修复 | 架构思维 |
|------|---------|---------|
| 字段未设置 | 各调用点手动设置 | 在创建/更新方法中统一设置 |
| 重复验证逻辑 | 每个接口都验证 | 在中间件或拦截器中统一验证 |
| 重复错误处理 | 每处都 try-catch | 在统一错误处理器中处理 |
| 重复日志记录 | 每处都写日志 | 在切面/拦截器中统一记录 |

## 决策流程

```
需要修改代码
    ↓
是否涉及多处修改？
    ↓ 是
是否有共同的底层入口？
    ↓ 是
能否在底层统一处理？
    ↓ 是
    → 在底层统一处理（最佳）
    ↓ 否
能否抽象出公共方法？
    ↓ 是
    → 提取公共方法
    ↓ 否
    → 各处修改，但添加注释说明原因
```

## 警示信号

当你发现自己在想：
- "复制这段代码到其他地方"
- "在所有调用点都加上这个"
- "这个字段每次都要设置"

**停下来！** 这正是需要架构思维的时候。

## 实际案例

### 案例：files_downloaded 字段

**问题**：上传包时 `files_downloaded` 字段没有设置

**错误做法**：
```go
// 在 10+ 个 adapter 中都添加
ver.FilesDownloaded = true
```

**正确做法**：
```go
// 在 repository 层统一处理
func (r *PackageRepository) StorePackageFile(..., ver *PackageVersion, file *PackageFile) {
    if ver != nil && file != nil {
        ver.FilesDownloaded = true  // 统一设置
    }
    // ...
}
```

**收益**：
- 只需修改 1 处
- 新增上传路径自动覆盖
- 符合"单一职责"原则
- 未来维护成本降低

## 总结

> **"不要在症状上打补丁，要在根源上解决问题。"**

每次修改前多花 5 分钟思考架构，可以节省未来数小时的维护成本。
